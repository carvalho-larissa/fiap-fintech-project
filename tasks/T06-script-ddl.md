# T06 — Script DDL (tabelas, constraints, índices)

| Campo | Valor |
|---|---|
| Status | ✅ Concluída |
| Tamanho | M |
| Depende de | T03 |
| Bloqueia | T07, T13 |
| Requisitos | RNF-01, RNF-02, RNF-06 |

## Objetivo
Criar o esquema físico completo no Oracle, fiel ao dicionário (T03), para que os comandos da atividade possam ser executados e validados.

## Contexto
O entregável não exige DDL, mas **sem ele nenhum comando pode ser testado** — e o modelo precisa refletir as evoluções (investimento, IDENTITY, CHECKs).

## Escopo
**Inclui:** as 10 tabelas, PK/FK/UK/CK, defaults, índices em FKs, comentários (`COMMENT ON`).
**Não inclui:** dados (T07), usuários/grants do banco.

## Especificação
Arquivos:
- `database/ddl/00-drop-tables.sql` — remove tudo em ordem reversa de dependência. Idempotente em 19c: bloco PL/SQL que ignora `ORA-00942` (tabela inexistente), **sem** `DROP TABLE IF EXISTS` (23ai-only, ver D-16).
- `database/ddl/01-create-tables.sql` — cria em ordem de dependência:
  1. `T_SF_USUARIO`, `T_SF_CATEGORIA`
  2. `T_SF_CONTA_BANCARIA`, `T_SF_META`, `T_SF_DIVIDA`
  3. `T_SF_RECEITA`, `T_SF_GASTO`, `T_SF_INVESTIMENTO`, `T_SF_APORTE_META`, `T_SF_PARCELA`

Regras de escrita:
- PK: `id_x NUMBER(10) GENERATED BY DEFAULT ON NULL AS IDENTITY` + `CONSTRAINT PK_… PRIMARY KEY` (D-02).
- Constraints **nomeadas** conforme T03 (nada de `SYS_C00…`).
- Defaults: `dt_cadastro`/`dt_criacao DEFAULT SYSDATE`, `ativo/ativa DEFAULT 'S'`, `T_SF_INVESTIMENTO.status DEFAULT 'ATIVO'`.
- FKs **sem** `ON DELETE CASCADE` (exclusão em cascata de dados financeiros é decisão de negócio, não assumida).
- Índices: `IX_<TABELA>_<COLUNA>` em toda FK `id_usuario`; índice composto `(id_usuario, dt_gasto)` em gasto e `(id_usuario, dt_aplicacao)` em investimento (atende RF-13/14/15).
- `COMMENT ON TABLE/COLUMN` ao menos para `T_SF_INVESTIMENTO` e colunas com domínio.
- Cabeçalho do arquivo: projeto, autora, versão, data, ordem de execução.
- FK composta `(id_conta, id_usuario)` → `T_SF_CONTA_BANCARIA(id_conta, id_usuario)` em receita, gasto e investimento, apoiada por `UNIQUE (id_conta, id_usuario)` na conta (D-14).
- `T_SF_PARCELA.dt_pagamento` anulável + `CHECK` de consistência com `status` (D-15).
- Taxas como fração decimal, `CHECK >= 0` (D-17).

## Critérios de aceitação
- [ ] `00` + `01` executam sem erro **duas vezes seguidas** (idempotência)
- [ ] `SELECT object_name, status FROM user_objects WHERE status <> 'VALID'` → 0 linhas
- [ ] 10 tabelas em `USER_TABLES` com prefixo `T_SF_`
- [ ] `USER_CONSTRAINTS` sem nome gerado pelo sistema (exceto NOT NULL)
- [ ] Testes negativos: `CHECK` rejeita `tipo = 'fixo'` (minúsculo) e `valor = -1`; `UNIQUE` rejeita e-mail duplicado; FK rejeita `id_usuario` inexistente; FK composta rejeita gasto com `id_conta` de outro usuário (`ORA-02291`, D-14)
- [ ] Sintaxe válida em 19c (nenhum recurso 23ai-only)

## Artefatos de saída
- `database/ddl/00-drop-tables.sql`
- `database/ddl/01-create-tables.sql`

## Riscos e notas
- A FK composta exige que a `UNIQUE (id_conta, id_usuario)` seja criada **antes** das tabelas filhas (ordem já garantida pela sequência acima).
