## Objetivo
Registrar e aprovar as decisões que o enunciado deixa em aberto, para que a escrita dos comandos não dependa de suposições. Cada decisão aprovada vira regra para T03–T16.

## Contexto
O enunciado exige operações sobre **investimentos**, conceito que **não existe** no modelo da Fase 3. Também não define geração de IDs, formato de datas nas máscaras nem o que "principais informações" significa no dashboard.

## Especificação
Publicar `docs/05-banco-de-dados/decisoes-tecnicas.md` com as decisões abaixo (formato: contexto → opções → decisão → consequências).

| ID | Tema | Decisão | Alternativa descartada / motivo | Status |
|---|---|---|---|---|
| D-01 | Tabela de investimentos | Criar `T_SF_INVESTIMENTO` (estrutura abaixo) | Reaproveitar `T_SF_META`/`T_SF_APORTE_META` — semântica diferente (meta ≠ aplicação financeira) | ✅ Aprovada |
| D-02 | Geração de IDs | Coluna **`IDENTITY`** em todas as PKs: `NUMBER(10) GENERATED BY DEFAULT ON NULL AS IDENTITY`. Os `INSERT` **omitem a coluna de ID**, exatamente como nos exemplos do enunciado (`INSERT INTO produto (nm_produto, vl_produto) VALUES (…)`) | `SEQUENCE` + `SQ_….NEXTVAL` — foge do formato dos exemplos do professor e adiciona um objeto por tabela. `BY DEFAULT` (e não `ALWAYS`) permite IDs fixos na massa de teste | ✅ Aprovada (critério: aderência ao enunciado) |
| D-03 | Datas nas máscaras | `TO_DATE('[DATA DO X]', 'DD/MM/YYYY')`; datas de sistema (`dt_cadastro`, `dt_criacao`) usam `SYSDATE` | Literal sem `TO_DATE` — depende de `NLS_DATE_FORMAT` da sessão (frágil) | Proposta |
| D-04 | Domínios de valores | Maiúsculas, sem acento, garantidos por `CHECK` (lista completa no dicionário, T03) | Texto livre — impede filtros e relatórios confiáveis | Proposta |
| D-05 | Senha | Coluna guarda **hash** (responsabilidade da aplicação). Nenhum `SELECT` retorna `senha`. O `UPDATE` de usuário **não** altera senha (troca de senha é fluxo próprio) | Atualizar senha junto do perfil — mistura responsabilidades e expõe o campo | Proposta |
| D-06 | Estilo do `UPDATE` | Atualização **completa** das colunas editáveis (padrão DAO `atualizar(obj)`). Nunca atualizar PK, `id_usuario`, `dt_cadastro`/`dt_criacao` | Um `UPDATE` por coluna — multiplica comandos sem ganho | Proposta |
| D-07 | Controle transacional | Entregável **sem** `COMMIT` (a aplicação/JDBC controla a transação). Scripts de teste usam `COMMIT`/`ROLLBACK` explícitos | `COMMIT` em cada comando — impede transações compostas no Java | Proposta |
| D-08 | Desempate de ordenação | "Mais recente" = `data DESC, id DESC` | Só `data DESC` — ordem não determinística em empates | Proposta |
| D-09 | Ambiente de validação | **Oracle Database Free em Docker**, rodando no **WSL2 (Ubuntu 24.04, já instalado)**. Credenciais apenas em arquivo local ignorado pelo git | Oracle FIAP — depende de senha e há risco de conflito com tabelas da Fase 3 no schema; fica como plano B | ✅ Aprovada |
| D-10 | Formato de entrega | **Documento Word → exportado para PDF**, contendo: (1) desenho(s) do modelo **relacional** (Fase 3, atualizado com investimentos); (2) os comandos SQL solicitados, cada um em seu item. **PDF é obrigatório** | `.sql`/`.txt` soltos — não atendem à instrução oficial | ✅ Aprovada (instrução oficial) |
| D-11 | Dashboard — "principais informações" | Usuário: `id_usuario`, `nome`, `email`, `dt_cadastro`. Última despesa: `id_gasto`, `descricao`, `valor`, `dt_gasto`, `tipo`. Último investimento: `id_investimento`, `nm_investimento`, `tipo`, `vl_aplicado`, `dt_aplicacao` | Incluir saldo/totais — amplia escopo e risco; melhoria futura | Proposta |
| D-12 | Dashboard — casos de borda | Usuário sem despesa e/ou sem investimento → **1 linha** com colunas nulas. Usuário inexistente → **0 linhas** | Retornar 0 linhas quando falta despesa — esconderia o usuário | Proposta |
| D-13 | E-mail único | `UNIQUE (email)` em `T_SF_USUARIO` (User Story 1, critério 3) | Validar só na aplicação — não protege contra concorrência | Proposta |
| D-14 | Conta pertence ao usuário | Validação na aplicação (FK simples, como no modelo). Melhoria futura: FK composta `(id_conta, id_usuario)` | FK composta agora — altera o modelo e complica os `INSERT` | Proposta |
| D-15 | `T_SF_PARCELA.dt_pagamento` | Tornar **opcional** (nula até o pagamento). No desenho da Fase 3 ela está obrigatória, o que impede registrar parcela em aberto/atraso (User Story 4) | Manter obrigatória — contradiz o próprio requisito de parcelas em atraso | Proposta |
| D-16 | Versão do Oracle alvo | Sintaxe compatível com **Oracle 19c** (ambiente FIAP) mesmo validando no Oracle Free 23ai: sem `IF [NOT] EXISTS`, sem tipo `BOOLEAN`, sem `SELECT` sem `FROM` | Usar recursos 23ai — quebraria no ambiente da faculdade | Proposta |

### Estrutura aprovada — `T_SF_INVESTIMENTO` (D-01)

| Coluna | Tipo | Nulo? | Regra |
|---|---|---|---|
| `id_investimento` | `NUMBER(10)` | Não | PK, `IDENTITY` (D-02) |
| `id_usuario` | `NUMBER(10)` | Não | FK → `T_SF_USUARIO` |
| `id_conta` | `NUMBER(10)` | Não | FK → `T_SF_CONTA_BANCARIA` (conta de origem do dinheiro) |
| `nm_investimento` | `VARCHAR2(150)` | Não | Ex.: "CDB Banco X 110% CDI" |
| `tipo` | `VARCHAR2(30)` | Não | `CHECK` ∈ {`CDB`,`LCI`,`LCA`,`TESOURO`,`ACOES`,`FII`,`FUNDO`,`POUPANCA`,`CRIPTO`,`OUTROS`} |
| `instituicao` | `VARCHAR2(100)` | Sim | Corretora/banco |
| `vl_aplicado` | `NUMBER(15,2)` | Não | `CHECK > 0` |
| `tx_rentabilidade` | `NUMBER(7,4)` | Sim | % a.a. (ex.: 12.5000) |
| `dt_aplicacao` | `DATE` | Não | Data usada para "mais recente" |
| `dt_vencimento` | `DATE` | Sim | `CHECK dt_vencimento >= dt_aplicacao` |
| `status` | `VARCHAR2(15)` | Não | `DEFAULT 'ATIVO'`; `CHECK` ∈ {`ATIVO`,`RESGATADO`,`VENCIDO`} |
