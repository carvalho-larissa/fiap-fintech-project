# T02 — Decisões técnicas (ADR)

| Campo | Valor |
|---|---|
| Status | ✅ Concluída |
| Tamanho | P |

## Objetivo
Registrar e aprovar as decisões que o enunciado deixa em aberto, para que a escrita dos comandos não dependa de suposições. Cada decisão aprovada vira regra para T03–T16.

## Contexto
O enunciado exige operações sobre **investimentos**, conceito que **não existe** no modelo da Fase 3. Também não define geração de IDs, formato de datas nas máscaras nem o que "principais informações" significa no dashboard.

Aprovação: D-01, D-02, D-09 e D-10 pela responsável; as demais foram delegadas pela responsável e decididas com base em boas práticas de desenvolvimento e modelagem.

## Especificação
Registro completo (contexto → decisão → consequências) em [`docs/05-banco-de-dados/decisoes-tecnicas.md`](../docs/05-banco-de-dados/decisoes-tecnicas.md). Resumo:

| ID | Tema | Decisão | Alternativa descartada / motivo | Status |
|---|---|---|---|---|
| D-01 | Tabela de investimentos | Criar `T_SF_INVESTIMENTO` (estrutura abaixo) | Reaproveitar `T_SF_META`/`T_SF_APORTE_META` — semântica diferente (meta ≠ aplicação financeira) | ✅ Aprovada |
| D-02 | Geração de IDs | `IDENTITY` em todas as PKs: `NUMBER(10) GENERATED BY DEFAULT ON NULL AS IDENTITY`. `INSERT` **omite a coluna de ID**, como nos exemplos do enunciado | `SEQUENCE` + `NEXTVAL` — foge do formato dos exemplos e adiciona um objeto por tabela. `BY DEFAULT` permite IDs fixos na massa de teste | ✅ Aprovada |
| D-03 | Datas nas máscaras | `TO_DATE('[DATA DO X]', 'DD/MM/YYYY')`; datas de sistema (`dt_cadastro`, `dt_criacao`) usam `SYSDATE` | Literal sem `TO_DATE` — depende do `NLS_DATE_FORMAT` da sessão | ✅ Aprovada |
| D-04 | Domínios de valores | Maiúsculas, sem acento, garantidos por `CHECK` (lista no dicionário, T03) | Texto livre — impede filtros e relatórios confiáveis | ✅ Aprovada |
| D-05 | Senha | Coluna guarda **hash** (responsabilidade da aplicação). Nenhum `SELECT` retorna `senha`. O `UPDATE` de perfil **não** altera senha | Atualizar senha junto do perfil — mistura responsabilidades e expõe o campo | ✅ Aprovada |
| D-06 | Estilo do `UPDATE` | Atualização **completa** das colunas editáveis (padrão DAO `atualizar(obj)`). Nunca atualizar PK, `id_usuario`, `senha`, `dt_cadastro`/`dt_criacao` | Um `UPDATE` por coluna — multiplica comandos sem ganho | ✅ Aprovada |
| D-07 | Controle transacional | Entregável **sem** `COMMIT` (a aplicação/JDBC controla a transação). Scripts de teste usam `COMMIT`/`ROLLBACK` explícitos | `COMMIT` em cada comando — impede transações compostas | ✅ Aprovada |
| D-08 | Desempate de ordenação | "Mais recente" = `data DESC, id DESC` | Só `data DESC` — ordem não determinística em empates | ✅ Aprovada |
| D-09 | Ambiente de validação | **Oracle Database Free em Docker** no **WSL2 (Ubuntu 24.04)**. Credenciais só em arquivo local ignorado pelo git | Oracle FIAP — plano B | ✅ Aprovada |
| D-10 | Formato de entrega | **Word → PDF** com (1) desenho(s) do modelo relacional atualizado e (2) os comandos SQL, cada um em seu item | `.sql`/`.txt` soltos — não atendem à instrução oficial | ✅ Aprovada |
| D-11 | Dashboard — "principais informações" | Usuário: `id_usuario`, `nome`, `email`, `dt_cadastro`. Última despesa: `id_gasto`, `descricao`, `valor`, `dt_gasto`, `tipo`. Último investimento: `id_investimento`, `nm_investimento`, `tipo`, `vl_aplicado`, `dt_aplicacao` | Incluir saldo/totais — amplia escopo (YAGNI); melhoria futura | ✅ Aprovada |
| D-12 | Dashboard — casos de borda | Sem despesa e/ou investimento → **1 linha** com colunas nulas. Usuário inexistente → **0 linhas** | 0 linhas quando falta despesa — esconderia o usuário | ✅ Aprovada |
| D-13 | E-mail único | `UNIQUE (email)` em `T_SF_USUARIO` (User Story 1, critério 3) | Só na aplicação — não protege contra concorrência | ✅ Aprovada |
| D-14 | Conta pertence ao usuário | **Integridade no banco**: `UNIQUE (id_conta, id_usuario)` em `T_SF_CONTA_BANCARIA` + **FK composta** `(id_conta, id_usuario)` em receita, gasto e investimento. Os `INSERT` não mudam | FK simples + validação só no Java — permitiria lançar gasto do usuário 1 na conta do usuário 2 | ✅ Aprovada (revisada: a proposta inicial superestimou o custo da FK composta, que é zero para os comandos) |
| D-15 | `T_SF_PARCELA.dt_pagamento` | **Opcional** (nula até o pagamento); `status = 'PAGA'` exige data | Manter obrigatória — impede registrar parcela em aberto/atraso (User Story 4) | ✅ Aprovada |
| D-16 | Versão do Oracle alvo | Sintaxe compatível com **Oracle 19c** (FIAP) mesmo validando no 23ai: sem `IF [NOT] EXISTS`, sem `BOOLEAN`, sem `SELECT` sem `FROM` | Recursos 23ai — quebrariam no ambiente da faculdade | ✅ Aprovada |
| D-17 | Representação de taxas | Taxas como **fração decimal** (`0.0299` = 2,99%): `tx_juros_mensal NUMBER(5,4)` (tipo da Fase 3 mantido) e `tx_rentabilidade NUMBER(7,4)`; `CHECK >= 0` | Percentual (`2.99`) — `NUMBER(5,4)` limitaria a 9,99% a.m., abaixo dos juros de cartão rotativo | ✅ Aprovada (nova) |

### Estrutura aprovada — `T_SF_INVESTIMENTO` (D-01)

| Coluna | Tipo | Nulo? | Regra |
|---|---|---|---|
| `id_investimento` | `NUMBER(10)` | Não | PK, `IDENTITY` (D-02) |
| `id_usuario` | `NUMBER(10)` | Não | FK → `T_SF_USUARIO` |
| `id_conta` | `NUMBER(10)` | Não | FK composta `(id_conta, id_usuario)` → `T_SF_CONTA_BANCARIA` (D-14) |
| `nm_investimento` | `VARCHAR2(150)` | Não | Ex.: "CDB Banco X 110% CDI" |
| `tipo` | `VARCHAR2(30)` | Não | `CHECK` ∈ {`CDB`,`LCI`,`LCA`,`TESOURO`,`ACOES`,`FII`,`FUNDO`,`POUPANCA`,`CRIPTO`,`OUTROS`} |
| `instituicao` | `VARCHAR2(100)` | Sim | Corretora/banco |
| `vl_aplicado` | `NUMBER(15,2)` | Não | `CHECK > 0` |
| `tx_rentabilidade` | `NUMBER(7,4)` | Sim | Fração ao ano (`0.1250` = 12,5% a.a., D-17); `CHECK >= 0` |
| `dt_aplicacao` | `DATE` | Não | Data usada para "mais recente" |
| `dt_vencimento` | `DATE` | Sim | `CHECK dt_vencimento >= dt_aplicacao` |
| `status` | `VARCHAR2(15)` | Não | `DEFAULT 'ATIVO'`; `CHECK` ∈ {`ATIVO`,`RESGATADO`,`VENCIDO`} |
