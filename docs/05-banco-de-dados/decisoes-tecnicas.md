## D-01 — Nova tabela `T_SF_INVESTIMENTO`
**Contexto.** O enunciado exige cadastrar, alterar, consultar, listar e exibir no dashboard **investimentos**. O modelo da Fase 3 não tem esse conceito. `T_SF_META`/`T_SF_APORTE_META` representam objetivos de poupança, não aplicações financeiras (sem tipo de produto, instituição, rentabilidade ou vencimento).
**Decisão.** Criar `T_SF_INVESTIMENTO`, ligada a `T_SF_USUARIO` e `T_SF_CONTA_BANCARIA`:

| Coluna | Tipo | Nulo? | Regra |
|---|---|---|---|
| `id_investimento` | `NUMBER(10)` | Não | PK, IDENTITY |
| `id_usuario` | `NUMBER(10)` | Não | FK → `T_SF_USUARIO` |
| `id_conta` | `NUMBER(10)` | Não | FK composta `(id_conta, id_usuario)` → `T_SF_CONTA_BANCARIA` (D-14) |
| `nm_investimento` | `VARCHAR2(150)` | Não | Nome do produto |
| `tipo` | `VARCHAR2(30)` | Não | `CDB`, `LCI`, `LCA`, `TESOURO`, `ACOES`, `FII`, `FUNDO`, `POUPANCA`, `CRIPTO`, `OUTROS` |
| `instituicao` | `VARCHAR2(100)` | Sim | Corretora/banco |
| `vl_aplicado` | `NUMBER(15,2)` | Não | `> 0` |
| `tx_rentabilidade` | `NUMBER(7,4)` | Sim | Fração ao ano (D-17), `>= 0` |
| `dt_aplicacao` | `DATE` | Não | Critério de "mais recente" |
| `dt_vencimento` | `DATE` | Sim | `>= dt_aplicacao` |
| `status` | `VARCHAR2(15)` | Não | `ATIVO` (default), `RESGATADO`, `VENCIDO` |

**Consequências.** Diagrama relacional precisa ser atualizado (T04). Segue as convenções da Fase 3 (`T_SF_`, `vl_`, `dt_`, `tx_`, `nm_`).

## D-02 — Geração de chaves primárias por `IDENTITY`
**Contexto.** A Fase 3 define PKs numéricas sem mecanismo de geração. Os exemplos do enunciado omitem a chave no `INSERT` (`INSERT INTO produto (nm_produto, vl_produto) VALUES (...)`).
**Decisão.** Todas as PKs: `NUMBER(10) GENERATED BY DEFAULT ON NULL AS IDENTITY`.
**Consequências.** `INSERT` sem coluna de ID, idênticos ao padrão do professor. No Java, o ID gerado é obtido com `getGeneratedKeys()`. `BY DEFAULT` permite IDs fixos na massa de teste; após a carga, as identities são reposicionadas (`START WITH LIMIT VALUE`). Requer Oracle 12c+ (FIAP: 19c).

## D-03 — Datas com `TO_DATE` explícito
**Contexto.** Literais de data dependem do `NLS_DATE_FORMAT` da sessão, que varia entre SQL Developer, JDBC e servidor.
**Decisão.** Máscara de data: `TO_DATE('[DATA DO X]', 'DD/MM/YYYY')`. Datas geradas pelo sistema (`dt_cadastro`, `dt_criacao`) usam `SYSDATE`.
**Consequências.** Comandos portáveis entre ferramentas; formato brasileiro legível no documento.

## D-04 — Domínios fechados, em maiúsculas, com `CHECK`
**Contexto.** Campos como `tipo` e `status` são categóricos. Texto livre gera variações (`Fixo`, `fixo`, `FIXO`) que quebram filtros e relatórios.
**Decisão.** Valores em maiúsculas, sem acento, garantidos por `CHECK`. Lista completa no dicionário de dados.
**Consequências.** A aplicação deve normalizar a entrada; o banco rejeita valores inválidos (`ORA-02290`).

## D-05 — Senha: somente hash, nunca retornada
**Contexto.** `T_SF_USUARIO.senha` é dado sensível.
**Decisão.** A coluna armazena hash gerado pela aplicação (ex.: BCrypt). Nenhuma consulta do entregável retorna `senha`. O `UPDATE` de perfil não altera a senha.
**Consequências.** Troca de senha será um fluxo próprio (fora do escopo). Consultas com lista explícita de colunas — `SELECT *` proibido.

## D-06 — `UPDATE` completo das colunas editáveis
**Contexto.** O enunciado pede "alterar os dados" de cada entidade.
**Decisão.** Um `UPDATE` por entidade atualizando todas as colunas editáveis (espelha o método `atualizar(obj)` do futuro DAO). Nunca no `SET`: PK, `id_usuario`, `senha`, `dt_cadastro`, `dt_criacao`.
**Consequências.** Um comando por requisito, reaproveitável diretamente no `PreparedStatement`.

## D-07 — Sem `COMMIT` nos comandos
**Contexto.** Quem define a fronteira da transação é a camada de aplicação.
**Decisão.** Comandos do entregável sem `COMMIT`. Scripts de carga e de teste controlam a transação explicitamente.
**Consequências.** Permite compor operações (ex.: cadastrar usuário + conta) numa única transação no Java.

## D-08 — Ordenação determinística
**Contexto.** Dois registros podem ter a mesma data; `ORDER BY data DESC` sozinho não garante ordem estável.
**Decisão.** "Mais recente" = `ORDER BY <data> DESC, <id> DESC`.
**Consequências.** Mesmo resultado a cada execução; o dashboard escolhe sempre o mesmo registro em empates.

## D-09 — Validação em Oracle Free (Docker/WSL2)
**Contexto.** Sem Oracle local; o servidor da FIAP exige credenciais e pode conter tabelas da Fase 3.
**Decisão.** Container `gvenzl/oracle-free` no Docker dentro do WSL2 (Ubuntu 24.04). Oracle FIAP como plano B.
**Consequências.** Ambiente descartável e reproduzível; credenciais só em `database/.env.local` (fora do git).

## D-10 — Entrega em PDF (Word → PDF)
**Contexto.** Instrução oficial: documento com o(s) desenho(s) do modelo relacional e os comandos SQL, exportado obrigatoriamente para PDF.
**Decisão.** DOCX gerado a partir do `.sql` validado e das imagens do diagrama; exportado para PDF.
**Consequências.** Fonte única do SQL (sem redigitação); verificação de aspas inteligentes no PDF final.

## D-11 — Conteúdo do dashboard
**Contexto.** "Principais informações" não é definido no enunciado.
**Decisão.** Usuário (`id_usuario`, `nome`, `email`, `dt_cadastro`) + última despesa (`id_gasto`, `descricao`, `valor`, `dt_gasto`, `tipo`) + último investimento (`id_investimento`, `nm_investimento`, `tipo`, `vl_aplicado`, `dt_aplicacao`).
**Consequências.** Escopo mínimo que atende ao enunciado; totais e saldo ficam como melhoria futura.

## D-12 — Dashboard com `LEFT JOIN`
**Contexto.** Usuário novo pode não ter despesas nem investimentos.
**Decisão.** Sempre 1 linha para usuário existente (colunas de despesa/investimento nulas quando não houver); 0 linhas para usuário inexistente.
**Consequências.** Tela do dashboard nunca "some" para usuários novos.

## D-13 — E-mail único
**Contexto.** User Story 1, critério 3: impedir dois usuários com o mesmo e-mail.
**Decisão.** `CONSTRAINT UK_T_SF_USUARIO_EMAIL UNIQUE (email)`.
**Consequências.** Garantia mesmo sob concorrência; a aplicação trata `ORA-00001` com mensagem amigável.

## D-14 — Conta deve pertencer ao mesmo usuário (FK composta)
**Contexto.** Receita, gasto e investimento têm `id_usuario` e `id_conta`. Com FKs simples, é possível registrar um gasto do usuário 1 numa conta do usuário 2 — inconsistência grave em sistema financeiro.
**Decisão.** `UNIQUE (id_conta, id_usuario)` em `T_SF_CONTA_BANCARIA` e FK composta `(id_conta, id_usuario)` nas três tabelas filhas (mantendo a FK para `T_SF_USUARIO`).
**Consequências.** Integridade garantida pelo banco, sem mudar nenhum `INSERT` (as colunas já existem). Revisão da proposta inicial, que previa só validação na aplicação.

## D-15 — `T_SF_PARCELA.dt_pagamento` opcional
**Contexto.** No desenho da Fase 3 a coluna é obrigatória, mas parcela em aberto ou em atraso ainda não tem data de pagamento (User Story 4).
**Decisão.** Coluna anulável; `CHECK` de consistência: `status = 'PAGA'` exige `dt_pagamento` preenchida.
**Consequências.** Diagrama atualizado (T04).

## D-16 — Compatibilidade com Oracle 19c
**Contexto.** A validação local usa Oracle 23ai; a FIAP usa 19c.
**Decisão.** Não usar recursos exclusivos do 23ai (`IF [NOT] EXISTS`, `BOOLEAN`, `SELECT` sem `FROM`, `GROUP BY` por alias).
**Consequências.** Scripts de drop idempotentes via bloco PL/SQL que ignora `ORA-00942`.

## D-17 — Taxas como fração decimal
**Contexto.** `tx_juros_mensal NUMBER(5,4)` (Fase 3) só comporta até 9,9999. Armazenado como percentual, impediria juros de cartão rotativo (> 10% a.m.).
**Decisão.** Toda taxa é fração: `0.0299` = 2,99%. Vale para `tx_juros_mensal` e `tx_rentabilidade`. `CHECK >= 0`.
**Consequências.** Tipo da Fase 3 preservado; a aplicação converte para exibição (`× 100`).
